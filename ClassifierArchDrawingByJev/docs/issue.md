# 既知の課題

最終更新: 2026-09-23

ここまでの実装(抽出タスク・通り芯分類・寸法線分類・壁分類・図面枠分類・読み取り不要情報分類)を通じて識別した既知の制約・未対応事項を分類して記録する。実装済みの詳細な経緯・判断理由は各`docs/adr/*.md`を参照。

## 1. 抽出タスク共通

- **フォント埋め込み未対応**: SVGは実際の埋め込みフォント(`AAAAAB+font0000000030638abc`等)ではなく代替フォント(`font-family="sans-serif"`)で描画している。グリフの字形・字送り幅が原本と完全には一致せず、通り芯番号等の文字位置にわずかな残差が残る(ADR0004)
- **複数ページPDF未対応**: 現状CLIの`--svg`・分類タスクは1ページ目のみを対象とする
- **線幅キャリブレーションの閾値は経験的**: サンプル選定基準(長さ閾値・孤立判定の余白・最低本数)はページ寸法やデータ分布から相対的に算出しているが、値そのもの(比率・係数)は本PDFで妥当性を確認したものであり、他のCADエクスポータ・スケールのPDFでは再調整が必要になる可能性がある(ADR0003)
- **中間データJSONの`linewidth`は生値のまま**: キャリブレーション係数(`linewidth_scale`)は別フィールドとして保持しており、`records`内の`linewidth`自体は未補正。分類ロジックで線幅を特徴量として使う場合、呼び出し側がこの係数を考慮する必要がある

## 2. 通り芯分類(`classify/grid.py`)

- **軸方向限定**: 水平/垂直の通り芯のみ対応。斜め通り芯は未対応(axis-aligned前提)
- **円形状限定**: 丸のみ判定。四角・六角形等の通り芯番号記号は非対応
- **重複GridLine**: 同じ通り芯の両端に円ラベルがある場合、同一線が2つの`GridLine`として重複検出される(dedupe未実装)
- **開いた円弧の誤検出リスク**: 円判定が点列の重心距離の相対標準偏差のみに基づいており、始点・終点が一致する閉ループであることの厳密なチェックがない
- **ラベル文字の読み順**: ラベル文字の連結はx0昇順のみで行っており、縦書きの複数文字ラベルがあると読み順が崩れる可能性がある
- **文字種制限**: ラベルの正規表現は英数字のみ(`^[A-Za-z]{0,3}[0-9]{0,3}$`)。ギリシャ文字・丸数字等の特殊フォントを使ったラベルは対象外
- **`sequence_plausible`は診断用のみ**: 同一系列内の連番妥当性は結果に記録するだけで、検出漏れ(欠番)の補完・推定は行っていない
- **寸法線との相互検証は未使用**: 「通り芯間には必ず寸法線がある」という性質は、寸法線分類(`is_axis_derived`)側からは通り芯を参照しているが、通り芯分類自体の検証・補強には使っていない

## 3. 寸法線分類(`classify/dimension.py`)

- **一点鎖線の交互リズム判定の閾値は経験的**: 「長い/短いを分ける倍率(2.5倍)」「間隔の許容比率(長い要素の50%以内)」「交互サイクルの最低回数(2回)」は本PDFの実測データに基づいて設定した値であり、線の粗密・縮尺が大きく異なる図面では再調整が必要になる可能性がある(ADR0007)
- **長短の二値分類のみ**: 一点鎖線(ダッシュ+ドット)は想定しているが、二点鎖線(ダッシュ+ドット+ドット)のような3種類以上の要素からなるパターンは考慮していない
- **1桁の寸法値を一律除外**: 数値ワードの桁数が2未満(カンマ除く)のものは誤検出防止のため除外している。この判断は「本図面の実寸法値は最小3桁」という観察に基づく前提であり、1〜2桁の正当な寸法(例: `50`のような小さい値)がある図面では検出漏れになる可能性がある
- **数値の読み方向は0°/90°のみ**: `matrix`から求めた読み方向で横書き/縦書きを判定しているが、斜め45°等の非直交な寸法線・注記には対応していない(通り芯・寸法線本体も軸並行前提のため、現状は整合している)
- **端部マーカー(丸)検出の閾値も経験的**: 探索半径(`_MARKER_SEARCH_TOLERANCE`)は本PDFの実測円サイズに基づく値
- **複数ページPDF未対応**: 抽出タスク・通り芯分類と同様の制約

## 4. 壁分類(`classify/wall.py`)

- **再現率(検出漏れ)が低い(最優先の既知課題)**: 誤検出(フローリング材ハッチング等の壁誤認)は「壁は閉じた直線に囲まれている」制約(leaf-pruningによる2-core抽出)の導入により解消したが、その代償として検出漏れが大幅に増えた。本PDFでの最終検証では、壁候補953件(nearest-neighborペア化後)のうち、最終的に壁と判定されたのは6件のみで、目視で明らかな建物外周・室内間仕切りの大半を検出できていない。原因は、実際の壁の対向面が装飾的なtick線・仕上げ表現(ハッチング等)に間を阻まれ、nearest-neighbor方式のペア化が真の対向面に到達する前に失敗する(または壁厚上限に達して打ち切られる)ケースが多いためと推定される。次回このタスクに着手する際の最優先課題(ADR0008)
- **ドア記号(扇形)検出が本PDFでは機能していない**: `geometry.find_arcs`(Kasa法による最小二乗円フィット)自体は正しく動作し194件の円弧を検出できるが、検出される円弧はすべて半径10pt未満の装飾的なアイコン(水栓・取っ手等)であり、実際のドア開閉記号(半径はドア幅相当、数十pt程度と推定)は1件も検出できていない。半径分布に明確な倍率ジャンプが存在しないため、装飾円弧の足切りも機能していない。スコア要素`door_adjacency`は実質ノイズ源になっている可能性がある
- **スコアの重み・閾値は経験的**: 壁厚上限比、隣接判定の許容差、各スコア要素の重み、部屋名・壁符号のキーワードリストは、本PDF1件での観察に基づく値であり、汎用性は未検証(ユーザー自身がスコアリング方式の性質上これを許容する前提で要件を出している)
- **ポリゴンの自己交差**: 非直交な屈曲を持つ壁では、簡易マイタージョインにより生成ポリゴンがわずかに自己交差する可能性がある
- **外壁との区別は未検証**: 要件上「内壁のみを対象とする」としているが、外壁を明示的に除外する専用ロジックはなく、候補生成・スコアリングの結果として内壁だけが残ることを期待する設計になっている。外壁が誤って壁として検出されるかどうかは本PDF(建物外周が敷地境界線等と入り組んでいる)では十分検証できていない

## 5. 図面枠分類(`classify/frame.py`)

- **外枠に接する装飾要素が図面枠として着色される**: 外枠の角にたまたま接する装飾要素(本PDFでは左上の方位マークの枠)が「外枠に接する直線」として図面枠に含まれる。図面枠・図面メタ情報を同色(`#ff00ff`)で出力する現状の要件では実害はないが、将来「外枠そのもの」と「それに接する装飾要素」を区別する必要が出てきた場合は拡張が必要
- **格子分割は単純な行×列の直積のみ**: 区画線が外枠の全幅/全高にわたる場合のみを対象とするため、L字型・階段状など複雑な表題欄配置には対応できない可能性がある(本PDFでの検証は水平1本の区画線のみ)
- **複数ページPDF・斜め方向の図面枠は未対応**: 他タスクと同様の制約

## 6. 読み取り不要情報分類(`classify/unread_info.py`)

- **ドア検出は装飾記号を密集クラスタとして除外するようになったが、本物のドアの発見には至っていない**: 半径・近接度で密集する弧群(断熱材の蛇腹記号・角丸四角の角等)を除外することで、誤検出は194件から6件まで減らせた(2026-09-23追記、ADR0010参照)。しかし残る6件も本物のドア記号である確証は無く、また廊下に実在するとユーザーが指摘した扉の扇形は、ベクターデータ・元PDFのラスター画像を調査しても該当する曲線オブジェクトが見つからず(該当箇所の扉は単なる直線1本のみで描画されていた)、位置を特定できていない。本物のドア記号がPDF上でどのようなベクター表現なのか、依然として未解明
- **点線閉ループ検出は密度の高い領域で完全に分離しきれない**: セグメント隣接グラフでのleaf-pruングにより「冷」アイコン等を含む137件を検出できるようになったが(2026-09-23追記、ADR0010参照)、ページ密度が高い領域では複数の独立したアイコンが1つの大きな連結成分として誤って統合されることがある
- **ハッチング判定の閾値は経験的、かつ検出漏れが残る**: 面の長さがランの間隔(中央値)の何倍以上あればハッチングとみなすか(チェーン構築前の事前フィルタ`_LENGTH_PREFILTER_RATIO_THRESHOLD`、構築後の事後フィルタ`_MIN_LENGTH_TO_GAP_RATIO`)、グループ化の倍率ジャンプ閾値(`_GAP_CLUSTER_RATIO_THRESHOLD`)はいずれも本PDFの実測データに基づく値であり、他のPDFでの再調整が必要になる可能性がある。**廊下・トイレ付近のハッチングは、線幅グループ内の長さ分布に明確な境界が無く事前フィルタが機能しないため検出できていない**(チェーン構築自体に長さ類似性チェックを組み込む再設計を複数方式試みたが、いずれも既存の正しい検出結果(会議室・夜警室)を悪化させたため見送った。2026-09-23追記、ADR0010参照)
- **軸並行のハッチングのみ対応**: 斜め45°等の非直交なハッチング(材質表現でよく使われる斜線ハッチング)は、既存の`collect_axis_aligned_lines`が軸並行の線しか扱わないため検出対象外。本PDFのフローリング材ハッチングは軸並行だったため実害はなかったが、汎用性には制約がある
- **検出器レジストリの拡張性は設計方針であり、まだ複数パターンでの実証はない**: 現時点では初版の3検出器のみで、実際に4つ目以降のパターンを追加する際に設計が想定通り機能するかは未検証

## 7. アーキテクチャ・設計上の留意点(課題ではなく既知の設計判断)

- 抽出タスクと分類タスクは疎結合(`classify`パッケージは`pdfplumber`・`extract.py`に依存しない)だが、分類タスク内部では`dimension.py → grid.py`、`wall.py → dimension.py, grid.py`への依存を許容している(ADR0005, ADR0008)。一方`frame.py`・`unread_info.py`は他の`classify/*.py`モジュールに一切依存せず、除外インデックス等は呼び出し側(`classify_cli.py`)が合算して渡す設計にしている(ADR0009, ADR0010)
- 半径・絶対座標・絶対pt値のハードコードは一貫して避け、ページ寸法や候補データ自身の分布から相対的に閾値を導出する方針を取っている。ただし「相対的な導出方法」自体(倍率・比率の値)は本PDF1件での検証にとどまっており、汎用性の実証には他のPDFでの検証が必要
- 壁分類はスコアリング方式(候補生成+複数根拠の加点+閾値判定)を採用しており、通り芯・寸法線のような決定的な判定条件とは設計思想が異なる。これはユーザー要件そのもの(「壁は決定的に決まらないためスコアリングを行う」)であり、対症療法ではなく意図的な設計判断(ADR0008)
- 読み取り不要情報分類は「検出器レジストリ」方式(独立した検出関数を並べるだけの構造)を採用しており、これもユーザー要件そのもの(「今後もこの分類パターンは増え続けるものとして設計して」)に基づく意図的な設計判断(ADR0010)
