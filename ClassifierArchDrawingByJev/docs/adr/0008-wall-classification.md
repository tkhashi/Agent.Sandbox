# ADR 0008: 壁(内壁)は候補生成+スコアリング方式で判定し、初版は再現率より誤検出防止を優先する

- ステータス: 採用(既知の制約あり、継続改善が前提)
- 日付: 2026-09-23

## コンテキスト

通り芯・寸法線に続き、壁(内壁のみ、外壁は対象外)の分類タスクを追加する要件があった。ユーザーからの要件は以下の通り:

- 壁は図面の詳細度によって描き方が変わり、通り芯・寸法線のように決定的な条件だけでは判定しきれない。そのため**スコアリング方式**(複数の根拠を加点し、最終的に閾値で合否判定する)を採用する
- 壁は単線ではなく、同一線種(線幅・色が同一)の平行な2本の直線で構成される(壁の両面)
- 加点根拠として以下4つが与えられた:
  1. 寸法線、または寸法線端部から直交方向に伸ばした仮想延長線の中心に壁が来ることが多い
  2. 「室」「トイレ」等の部屋名文字列を四方から囲む直線群は壁の片面であることが多い
  3. ドア記号(扇形、直線または点線の円弧)の連なり・開口方向に壁が連続することが多い
  4. 一定の閾値未満で並行する2直線が連続している場合(方向転換を許容)は壁であることが多い
- 出力はスコアに応じたグラデーション塗りつぶし(高: `#ff69b4`、低: `#66cdaa`、いずれも不透明度50%)

実装を進める過程で、ユーザーから追加の制約が示された:

- 壁は必ず**閉じた直線(部屋を一周する輪郭)**に囲まれている。閉じていない場合は壁ではない
- 通り芯・寸法線を構成する線は壁ではないので除外する
- 壁が極端に厚いことはないので上限閾値を設ける
- 部屋の種類に「PS」「EPS」を追加する
- 壁付近には「W」(壁符号、例: 「W1」)や「壁」という文字があることがある(=5つ目の加点根拠)

## 決定

### 1. 候補生成(Phase A)+スコアリング(Phase B)の2段構成

1. **候補生成**: 軸並行(水平/垂直)の`line`を線幅ごとにグループ化し、同一座標に密集する断片を1本の「面」にまとめた上で(`_merge_axis_faces`)、各面をその面より座標が大きい側で最初に条件(同一線幅・十分な重なり・壁厚として妥当な間隔)を満たす面と**nearest-neighbor方式で1対1にペア化**する(`WallPairSegment`)。全組み合わせを総当たりでペア化する方式は、フローリング材のハッチング等、同一線幅の面が多数並ぶ箇所で組み合わせ爆発を起こし、かつ後段の閉ループ判定を欺くほど密なグラフを作ってしまうことが実データで判明したため、nearest-neighborに変更した
2. **閉ループ制約**: 「壁は必ず閉じた直線に囲まれている」という要件を、`WallPairSegment`のセンターライン端点を結ぶグラフに対する**leaf-pruning(2-core抽出)**として実装する(`_prune_to_closed_loops`)。次数1のノード(行き止まり端点)を持つ辺を繰り返し取り除き、残った辺だけを壁候補として採用する。フローリング材等のハッチングは、nearest-neighbor化により互いに端点を共有しない独立した辺の並びになるため、この枝刈りで自然に除去される
3. 通り芯(`GridLine.segment_indices`)・寸法線(`DimensionSegment.line_indices`・`start/end_extension_indices`)を構成する`line`のインデックスは、候補生成の時点で除外する
4. 壁厚の上限を、まずページ対角線比(`_MAX_WALL_THICKNESS_PAGE_RATIO`)で大まかに制限し、さらに実際の間隔分布の自然な倍率ジャンプ(`split_by_relative_jump`、通り芯分類の一点鎖線検出で確立した手法を汎用化したもの)で絞り込む
5. 閉ループを構成する候補を、方向転換を許容して連結し`WallRun`とする(`_chain_pair_segments`)。連結順に沿った簡易マイタージョインでポリゴン化する(`_build_polygon`)

### 2. スコアリング5要素

`WallRun`ごとに以下5つを加点する(各関数は`classify/wall.py`参照):

- `dimension_symmetry`: 壁センターラインが寸法線の中心点、または寸法線端部からの直交方向仮想延長線と一致するか(`_score_dimension_symmetry`)
- `room_enclosure`: 部屋名ラベル(`_ROOM_KEYWORDS`に「PS」「EPS」を含む)から上下左右にレイキャストし、最初にヒットする壁候補に加点(`_score_room_enclosure`)
- `door_adjacency`: `geometry.find_arcs`(開いた円弧、Kasa法による最小二乗円フィット)で検出したドア記号候補の中心が、壁候補センターライン上/近傍にあるかで加点。装飾的な小さい円弧(水栓・取っ手等)は半径分布の自然な倍率ジャンプで除外を試みるが、本PDFでは明確な閾値が見つからず、有効な足切りができていない(下記「既知の制約」参照)
- `wall_label`: 「W」+数字(例: 「W1」)または「壁」という文字列が壁候補の近傍にあるかで加点(`_score_wall_label`)
- `parallel_continuity`: 連続長のページ対角線比、厚みの分散の小ささから加点。候補生成そのものの基準でもあるため、他の4要素と異なり「候補になった時点で最低限のスコアを持つ」という性格を持つ

最終的な合否は`score >= threshold`で判定する。`threshold`はスコア分布の自然な倍率ジャンプ(`split_by_relative_jump`)から導出し、境界が見つからない場合はフォールバック定数(`_WALL_SCORE_THRESHOLD_RATIO = 1.0`)を使う。

### 3. 「4根拠のうち1つ以上の加点を必須とする」ルールは撤回した

実装初期には「`parallel_continuity`だけでは合格させず、他の4要素のいずれか1つ以上の加点を必須とする」というルールを設けていたが、後から追加された「閉じた直線」制約によって候補生成の時点で強い構造的フィルタが働くようになったため、このルールは撤回した(閉ループを構成しない偽陽性は候補にすら残らないため、`parallel_continuity`のみでの合格を許容しても実害が小さいと判断した)。

### 4. ポリゴン化はline-network-trace方式を採用(rectangle-union不採用)

`WallRun`のポリゴンは、連結順に沿って両面をオフセットしたリボン状の頂点列として生成する(単一区間なら矩形、屈曲部は単純な頂点列の連結による簡易マイター)。rectangle-union(各区間を矩形として和集合を取る)方式は、一般的なポリゴン演算(shapely等)への依存追加が必要になるため採用しなかった。非直交な屈曲では頂点がわずかに自己交差しうるが、本図面の壁はほぼ直交であるため実用上の問題は小さいと判断する。

### 5. `render.py`への`FillPolygon`/グラデーション拡張

`build_svg`に`fill_polygons: list[FillPolygon] | None = None`という新規オプション引数を追加した(既存呼び出しは無変更)。`FillPolygon(points, color, opacity=0.5)`は「ポリゴン+色+不透明度」のみを持つ汎用的なデータで、`render.py`は「壁のスコア」という概念を一切知らない(`highlight_indices`と同じ責務分離)。スコア→色のグラデーション変換(`_gradient_color`)は`render.py`側に置くが、スコアの意味自体は`classify_cli.py`が解決してから渡す。

## 理由

- 絶対値のハードコードを避け、データ分布から相対的に閾値を導出する方針(ADR0003/0006/0007)を、壁厚上限・スコア閾値・ハッチング除外等にも一貫して適用した
- 「閉じた直線」制約は、誤検出(特にフローリング材ハッチングを壁と誤認する問題)を構造的に解消する強力な手がかりであり、スコアによる後付けの足切りよりも根本的な解決になった
- 「4根拠のうち1つ以上必須」ルールは、閉ループ制約という、より根本的で確実なフィルタが導入されたことで冗長になったため撤回した。スコアの4要素はあくまで確度を示す付加情報として扱う

## 既知の制約(初版時点)

このタスクは通り芯・寸法線分類と異なり、**実データでの精度検証が途上**である。特に以下は明確な既知の課題として残す(`docs/issue.md`にも記載):

- **再現率(検出漏れ)が低い**: 本PDFでの最終実行結果は、壁候補953件(nearest-neighbor化後)のうち、閉ループ制約を通過したのはごく一部で、最終的に壁と判定されたのは6件のみだった。目視で明らかに壁と分かる建物外周・室内間仕切りの大半が候補生成の時点で捉えられていない。原因は、実際の壁の対向面が、間に挟まる装飾的なtick線・ハッチ・仕上げ表現等によって、nearest-neighbor方式では真の対向面に到達する前に候補生成が失敗する(または`precheck_cap`到達で打ち切られる)ケースが多いためと推定される。誤検出(ハッチングの壁誤認)は解消できたが、代償として検出漏れが増えており、両者のバランスは今後の調整課題である
- **ドア記号検出(`find_arcs`)は本PDFで実質機能していない**: Kasa法による円フィット自体は正しく動作し194件の円弧を検出できたが、検出される円弧はすべて半径10pt未満の装飾的なアイコン(水栓・取っ手等)であり、実際のドア開閉記号(半径はドア幅相当、本PDFの寸法体系から数十pt程度と推定)は1件も検出できなかった。半径分布に明確な倍率ジャンプが存在しないため、装飾円弧の足切りも機能していない。`door_adjacency`スコアは事実上ノイズ源になっている可能性があり、次回精度検証の優先対象とする
- **スコアの重み・閾値は経験的**: 他の判定要素(壁厚上限比、隣接判定の許容差等)と同様、本PDF1件での観察に基づく値であり、汎用性は未検証
- **多角形の自己交差**: 非直交な屈曲を持つ壁では、簡易マイタージョインにより生成ポリゴンがわずかに自己交差する可能性がある
